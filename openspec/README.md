# OpenSpec (Fission-AI)

Spec-driven development for courier-outbox using the [Fission-AI OpenSpec](https://github.com/Fission-AI/OpenSpec) CLI (`@fission-ai/openspec`). **Specs describe current behaviour. Changes describe intended work.** Non-trivial code does not land without an approved change.

## Prerequisites

- Node.js ≥ 20.19
- CLI installed and on `PATH`:

```bash
npm install -g @fission-ai/openspec@latest
export PATH="$(npm prefix -g)/bin:$PATH"
openspec --version
```

## Layout

```
openspec/
├── config.yaml           # Schema, project context, artifact rules (read by CLI + agents)
├── project.md            # Human-readable project notes (optional; context also in config.yaml)
├── specs/                # Source of truth: one folder per capability
│   ├── README.md         # Capability index + SRS mapping
│   └── <capability>/spec.md
└── changes/              # Active proposals + archive/
    ├── <change-id>/      # proposal.md, tasks.md, design.md, specs/… deltas
    └── archive/          # Completed changes after merge
```

Cursor wiring (committed, generated by `openspec init --tools cursor`):

- `.cursor/skills/openspec-*` — agent skills for propose / apply / archive / sync / update / explore
- `.cursor/commands/opsx-*` — slash commands: `/opsx-propose`, `/opsx-apply`, `/opsx-archive`, …

Refresh after CLI upgrades: `openspec update --force`.

## When a change proposal is required

| Needs a proposal | Does not |
|------------------|----------|
| New endpoint, CLI command, table, or migration | Typo / comment / docs wording |
| Delivery semantics, retries, signing, SSRF policy | Dependency patch bumps |
| New config variable or external dependency | Refactor with no behaviour change |
| Anything touching an SRS FR/NFR | Test-only additions for existing behaviour |

When unsure, propose a change.

## Workflow (CLI + Cursor)

1. **Propose** — `/opsx-propose` or skill `openspec-propose`. Pick a kebab-case change id (e.g. `add-event-enqueue`). The workflow creates `openspec/changes/<id>/` with proposal, tasks, optional design, and spec deltas.
2. **Approve** — Review the PR; set `Status: approved` in `proposal.md` before implementation.
3. **Apply** — `/opsx-apply` or `openspec-apply-change`. Implement code; tick `tasks.md` as commits land.
4. **Validate** — `openspec validate <change-id> --strict` (or `openspec validate --all` for specs).
5. **Archive** — After merge: `/opsx-archive` or `openspec archive <change-id> --yes`. Deltas fold into `openspec/specs/`; the change moves under `changes/archive/`.

Exploratory work: `/opsx-explore`. Refresh skills/commands: `/opsx-sync` or `openspec update --force`.

## Requirement format

```markdown
### Requirement: Idempotent enqueue
The system SHALL return the original event when the same API key reuses an idempotency key.

#### Scenario: Duplicate key replays
- **WHEN** a producer POSTs /v1/events twice with the same idempotency_key
- **THEN** the second response is 200 with header `Idempotent-Replay: true`
- **AND** only one event row exists
```

Use SHALL/MUST for normative statements. Reference SRS ids in requirement text where applicable.

## Agent entrypoints

Read `AGENTS.md`, then `openspec/config.yaml` context and this file. Do not hand-edit `openspec/specs/<capability>/spec.md` for unmerged features — use change deltas and archive.
